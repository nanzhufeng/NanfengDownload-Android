# 可迁移开发经验

更新时间：2026-10-11（Asia/Shanghai）；本轮仅追加146已验证经验，既有规则不重复沉淀。
依据：`android/` 当前源码、Git 历史、`PROJECT_HANDOFF.md` 与 `docs/verification/`。本文件不把历史平台行为或设备证据包装成通用定律。

## 一、通用原则

### 1. 把“成功”拆成可验证的真实对象

来源解析、任务入队、网络响应、临时文件、系统媒体库、历史记录和可播放性是不同状态。应让各层有唯一所有者，并让 UI 读取持久事实，而不是用页面提示推断完成。南枫下载以 `DownloadRepository`、`TaskTransitionPolicy`、`MediaStoreOutputStore` 和 `DownloadHistory` 分离这些事实。

### 2. 外部来源要先验证身份与作用域，再谈解析效率

短链、页面数据、Cookie、重定向和 CDN 都是外部不稳定输入。先约束官方域名、作品 ID、目标主机、数量和凭据作用域；未知但官方的新路由可交给受控解析器，非官方跳转必须失败。该原则来自 `UrlClassifier.kt`、Python `_resolve_known_short_link`、`SessionAccessPolicy` 与 HTTP 下载器的主机级凭据过滤。

### 3. HTTP 成功不是成品成功

应验证预期长度、媒体魔数/容器、重定向后的实际 URL、输出后可读性，并在失败时不发布。`HttpFileDownloader`、`MediaFileValidator` 与 `MediaStoreOutputStore` 共同证明：提前 `206`、空体、HTML 错页、截断 WebP 和被重定向的资源都可能在 HTTP 层看似成功。

### 4. 持久任务必须设计恢复、幂等与可解释失败

进程死亡、断网和取消是常态。任务需可恢复、可重试，完成历史去重必须与“用户删除历史后允许重新下载”并存；失败保留中文原因和建议。此原则由 Room migration、`RoomDownloadRepository`、`ForegroundDownloadWorker`、`DownloadTaskRunner` 和 v1.2.7 记录支持。

### 5. 真实产物的发布应可回滚且不覆盖用户数据

先写临时/Pending 目标，成功复核后完成发布；只清理本次创建的输出。文件命名冲突生成新副本而非覆盖。`MediaStoreOutputStore` 对 MediaStore 与 SAF 两条路径都实现这一规则。

### 6. 验收必须按证据层级报告

单测、lint、隔离模拟器、真机安装、真机用户路径和外部服务都只能证明各自一层。v1.2.82 的命令证据、用户随后确认的 14 张人工无水印验收、2026-10-08 受控网站与尚未测试的 Pornhub 真实站点都应分别记录，避免夸大结论。

### 7. 安全门禁应在构建系统中失败关闭

重要禁止项不能只依赖口头约定。该项目在 Gradle 中使所有 `connected*AndroidTest` 依赖一个直接失败的任务；Release 签名不完整同样失败。对含用户数据的设备，这是低维护、可审计的防护。

### 8. 提取器返回值也要经真实网页结构反证

不要把第三方提取器字段名当语义保证：yt-dlp Generic 直链格式的 codec 键可能存在但值为 `None`；多个 HTML 嵌入视频的 `webpage_url` 可能全部指向同一合集页。需要保留目标来源身份、核对成员的独立媒体 URL，并通过可控网页加真实下载回归。依据：`web_media.py`、`web_collection.py`、对应 Python 测试及 2026-10-08 隔离模拟器记录。

### 9. 146增量：提交游标、首尾完整性与冻结交付

并行进度不能代写持久提交游标；无损封装需要验证首尾帧与真实时间轴；宿主回归不能污染嵌入运行时打包目录；冻结源码清单必须覆盖全部受控生产文件。这些通用规则已增量写入个人 `develop-apps-with-nanfeng-product-standards` 的既有诊断/交付references与审计模板，不另建Skill或竞争正文。

项目根因、分类和可执行资产见[146正式经验增量审计](verification/2026-10-11-app-experience-increment-audit.md)；项目封装及恢复具体约束由[传输合同](download-transfer-policy.md)维护。其他容器、编码、网络与设备需在目标项目重新验收，不能复制本样本数量或吞吐结论。

## 三、不可直接照搬的部分

1. **平台字段、URL 路由与 UA。** `urlList`、`tplv-dy-water`、抖音短链、xhs CDN 和 TikTok 会话行为都可能变化；其他平台应重新发现其来源契约，不能复制字符串规则。
2. **并发数字与 Range 阈值。** `PlatformTransferPolicy` 的连接数、全局预算 8、抖音图集串行是当前网络/服务端实测后的取舍，不能外推为普适最优值。
3. **Android/OPPO 安装策略。** `pm install -r --user 0`、证书谱系、数据 inode 对这一设备与产品有效；其他系统、签名链和用户数据模型必须另建门禁。
4. **固定依赖版本。** 当前 AGP、Compose、Media3、Chaquopy、yt-dlp、NDK 和 LAME 版本是可复现基线；迁移到其他应用前必须验证兼容、许可证和构建产物。
5. **历史验证数量。** v1.2.8 的 OPPO 单视频闭环、v1.2.82 的图集证据都只对应当时样本和版本，不能替代今天的新样本或其他平台验收。
6. **通用提取器与明文 HTTP 范围。** 当前产品为对齐 HTTP(S) 网页启用应用级明文流量，且通过 yt-dlp Generic/有限网页捕获处理其他站点；它不是其他产品默认应该照搬的安全或网站支持承诺。复杂音轨、DRM、会员和站点反爬须逐样本决定。

## 四、文档冲突与正确取证顺序

2026-10-08审阅时，`README.md` 的1.2.67/1.2.48及旧 `context.md` 与当时源码冲突。146发布已同步README；旧context不再作为当前入口。当前context使用完整开发档案与PROJECT_STATUS，历史冲突保留日期，不把旧差异写成今天的缺陷。

跨项目复用时按以下顺序取证：当前代码与构建配置 → 当前测试/产物/设备回读 → 当前交接与验证记录 → 历史计划和 README → 记忆。发生冲突时记录差异、使用前者，不用“更新文档”替代重新验证。

## 五、建议复用方式

- 复用原则和证据模型，不复制平台分支。
- 先为新产品指定状态所有者、输出事务边界、设备数据安全边界和验证矩阵。
- 将高风险的禁止项编码成构建/CI 门禁；将临时样本、版本和设备状态留在动态交接，不写进全局规则。
- 使用 `.agents/skills/` 下的开发、排错、测试、审查和文档同步 Skill 时，仍以目标项目当前源码为最终事实源。
