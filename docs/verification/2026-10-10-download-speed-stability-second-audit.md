# 下载速度与稳定性第二轮审计

日期：2026-10-10。仅隔离 emulator-5580/NanfengWebParityTmp；以实际分阶段耗时、最终媒体和正常 UI 为证据。普通传输目标至少 1 MB/s，长视频目标 5–10 MB/s 以上；MB/s 按十进制字节计算，不把局部峰值或本地夹具速度称为所有平台达标。

## 修复和根因

- HTTP 408/429/500/502/503/504 增加有限重试，保留已下载前缀；遵循 Retry-After 秒数/HTTP 日期，超过本次最大等待的服务器冷却明确失败，不提前重试。取消可及时打断冷却，401/403/404/410/416仍由既有来源重解析处理。区间响应的起点、终点、总量及超长响应继续严格验证。
- YouTube 4 MiB 视频请求块允许多个有界区间并行；视频/音频预算按需求分配，同一任务由旧 4+1 提升到 6+1，保持总预算及音频单连接。没有用无界并发、增加假下载字节或舍弃旧前缀提速。
- HLS/DASH 原生分片最多 6 个连接，顺序组装；修复一个失败工作线程提前关闭共享输出、连带破坏健康片段的问题。缺片明确失败，恢复片段后使用保存计划续传。过期源错误不会被健康线程抹掉。
- 分片网络读取用 256 KiB 缓冲，缓存 Java 方法引用，网络吞吐通知限制 4 Hz，取消仍动态检查；记录清单、纯片段传输、时间线、封装耗时。单流下载结束进入真实封装阶段，避免将封装误报为网络停滞。
- 新独立音视频合并使用现有 Media3 1.7.1 进程内压缩样本路径，无重新编码。仅成功且实际含视频帧/音频样本才原子替换私有缓存；取消/失败保留来源及旧输出，临时输出使用每次唯一文件名。原 TS 封装解析没有切换。
- 新合并器首轮长视频出现音频累计偏移，不能以解码成功宣布合格。现场定位 Media3 1.7.1 固定音频 48 kHz 时基、逐样本时长取整；44.1 kHz 长音频实测偏移 1.492 秒。修正为先将绝对时间戳对齐各轨时基再交给封装器，回归覆盖 161,961 个 AAC 样本及小数视频帧率。126 的 URI180只保留失败时间戳证据，不计最终合并验收。

## 网络设置审计纠正

119报告只核验 legacy http_proxy 为 null，遗漏 canonical global_http_proxy_host/port 的本任务临时代理残留，因此其中“直连/代理”标签不足以证明实际路由因果。120后的检查发现 host/port 精确等于本任务临时设置，已仅清除此匹配残留；最终必须核验 legacy、host、port、exclusion、PAC五字段均无代理。本报告保留旧测量，不沿用其路由因果结论。此前 YouTube 0B登录/机器人校验失败在清理后已通过正常重试恢复，不再声明账号阻塞。
